# Errors

My mistake log. Every query I got wrong in a way worth remembering, copied exactly as I wrote it. Newest at the bottom.

| Date | What I wrote | What was wrong | The rule I learned |
|---|---|---|---|
| 2026-10-07 | `SELECT name, plan FROM accounts WHERE country LIKE "DE%" ;` | Double quotes mean a column or table name, so Postgres looked for a column called `DE%` (`column "DE%" does not exist`). And `LIKE 'DE%'` means "starts with DE" when I wanted an exact match. | Single quotes for text values, double quotes for column and table names. Use `=` for exact matches, `LIKE` only for patterns. |
| 2026-10-07 | `plan NOT = 'free'` | Syntax error. `NOT` goes in front of a whole condition (`NOT plan = 'free'`), not in front of the `=`. My next try, `plan NOT LIKE 'free'`, worked but said "doesn't match a pattern" when I meant "isn't equal to". | "Not equal" is `<>` (Postgres also accepts `!=`). Use the operator that says what I mean. |
| 2026-10-07 | `SELECT * from invoices WHERE id, amount >= 25;` | Columns to show go after `SELECT`, and `WHERE` only takes conditions, so `WHERE id, amount ...` is a syntax error. Also "over 25" is `>`, not `>=`. | Columns go in `SELECT`, conditions go in `WHERE`. Read `>` and `<` out loud with the column first. |
| 2026-10-08 | `SELECT id, issued_at FROM invoices BETWEEN 2026-09-01 AND 2026-09-30;`<br>then `SELECT id, issued_at FROM invoices WHERE issued_at BETWEEN 2026-09-01 AND 2026-09-30;`<br>then `SELECT id, issued_at FROM invoices WHERE issued_at BETWEEN '2026-09-01 AND 2026-09-30';` | First: no `WHERE`, no column to check, no quotes on the dates. Second: without quotes, 2026-09-01 is a sum (2026 minus 9 minus 1), so Postgres complains about comparing a date with a number. Third: one pair of quotes around the whole range, so Postgres reads it as a single (broken) date. | `WHERE column BETWEEN 'start' AND 'end'`. Each value gets its own quotes, and keywords stay outside them. |
| 2026-10-08 | Predicted 1 row for `WHERE plan = 'free' OR plan = 'pro' AND country = 'DE'` | I read it as "(free or pro) and in Germany". But `AND` is applied before `OR`, so Postgres reads `plan = 'free' OR (plan = 'pro' AND country = 'DE')`. 3 rows. | `AND` happens before `OR`. If I mix them, I add brackets so nobody has to remember. |
| 2026-10-08 | `SELECT name, role FROM employees WHERE building = NULL;` (SQLBolt lesson 8) | `=` asks "is this the same as something unknown?", and the answer is always unknown, even when the building really is NULL. It doesn't error, it just returns nothing. | Find NULLs with `IS NULL` or `IS NOT NULL`. Never `= NULL` or `<> NULL`. |
| 2026-10-08 | Said `WHERE amount <> 25` means "exactly 25" | Wrong way round: `<>` means not equal. I'd used it the day before (`plan <> 'free'`) and still flipped it. And NULL still drops out: is unknown not equal to 25? Unknown, so invoice 107 is gone. | `<>` is "less than or greater than", so anything except that value. If NULL rows should be kept, say so: `OR column IS NULL`. |
